ovid RS Reference Guide

Remote sensing archive: what the app does to every drone image, log and dataset it finds, why, and how to check it. For RS 0.5.0 (ovid Core 1.14.0). ovid RS is a catalogue, provenance and positioning-status tool; it does not process imagery. The archive is never changed: files are only read, and nothing is written inside a source. Settings are quoted with their defaults; change them in CFG at the top of rs_pipeline.R or in the files under <project>/config/.

Quick start

  1. Open the app: double-click Open RS (Mac).command in Ovid_Apps (or Ovid_RS.bat on Windows). Packages install themselves on the first start.
  2. On Sources, press Browse… to pick a drive or folder (for example an external disk with the flight archive), give it a short name and press Scan folder. The first scan opens every image once; later scans only read folders whose files changed.
  3. On Map, every flight appears on satellite imagery, coloured by positioning status. Click a flight on the map or in the table to see it beside the map.
  4. On Flight, give it a display name, project and site, and confirm or reject the files linked to it. Everything you type is saved to config/ and backed up.
  5. On QA, work through the flights with flags and the files tied to no flight.
  6. On Sources, press Create viewer, then Export viewer (ZIP), to send the catalogue to someone without R.

From the command line:

Command What it does
Rscript rs_pipeline.R scan <folder> <name> adds the folder as a source (or rescans it) and rebuilds the catalogue
Rscript rs_pipeline.R rescans every source that is plugged in; the others keep their last scan
Rscript rs_pipeline.R export writes the viewer: <project>/output/viewer/Ovid_RS_viewer.zip
Rscript rs_pipeline.R gnss out.csv a.csv b.txt stitches GNSS survey files into one CSV

One image traced through

A DJI Matrice 350 RTK image taken with a Zenmuse P1, in a mission folder named DJI_202001011200_001_Site-A.

  1. Found. The scan lists the file: .JPG, 18 MB, in source T7. Format jpg, role image.
  2. Read. Its first 64 kB give DateTimeOriginal 2024:07:12 10:42:07, latitude and longitude, drone-dji:RelativeAltitude +60.1 m, RtkFlag 50 and the camera serial.
  3. Time. DJI cameras write UTC in the XMP (UTCAtExposure), so time_utc is used as written and no zone rule is needed.
  4. Flight. The images from this camera in this folder are sorted by time. The gap to the image before is 2 s, so it belongs to the same flight; the next gap of 14 min starts a new flight. The flight’s id is built from the camera serial and the first exposure in UTC.
  5. Site. From the folder name: Bog. The -P1 suffix is not trusted for the sensor; that comes from the image metadata.
  6. Links. DJI_202001011200_001_Timestamp.MRK in the same folder: same folder 0.5, time in the file name within the flight +0.4, so the score is 0.9 and the link is auto.
  7. Status. 412 of the flight’s 420 images have RtkFlag 50 (fixed): 98.1 %, which is 95 % or more, so the flight is RTK corrected. The evidence column says so in words.
  8. Map. The image positions draw the observed outline (solid) in the RTK colour.

1. Sources and scanning

A source is one drive or folder with archived data. Sources are listed in config/sources.csv (id, path, label, added). The same flight on several sources is one flight with copies: copies are found by the flight id, not by the path.

  • Every photo’s header is read (the first 64 kB, where EXIF and XMP sit), once. The result is kept per file in <project>/cache/sources/<source>/exif.rds, by path, size and modified time, so a rescan reads only new or changed photos.
  • Only drone photos make flights: a photo counts when it carries a drone tag (DJI drone-dji, senseFly or Camera: XMP) or its EXIF make and model match a row of config/drone_cameras.csv (Set-up tables; make in any case, model as a prefix, a blank model for any model of that make; a row with drone "no", such as DJI's handheld Osmo and Pocket cameras, wins over a drone tag). Other photos (phones, compact cameras, trail cameras, DSLRs, screenshots) are left out and listed in catalogue/other_photos.csv with why.
  • The same photo in several folders or sources (by size, camera serial, exposure time and band; without an EXIF time, size and the md5 of the first 64 kB) is counted once; the copies are listed in catalogue/duplicates.csv (kind, key, kept_path, dup_path, why), which the eMotion logs share.
  • A source inside another source (real paths compared) keeps its own files: each file is counted once, under the innermost source. The Sources page says so before such a folder is scanned, and marks the sources “inside” or “contains”.
  • Satellite scenes (TIFF, JP2 or NITF beside .IMD, .TIL or DIMAP metadata, or with a satellite name) are rasters, never photos or flights.
  • Remove (Sources page) takes a source out of config/sources.csv and its rows out of the catalogue. Its folder and files are never touched.
  • A source that is not plugged in keeps its last scan. Its flights stay in the catalogue and the Sources page shows it as not connected.
  • config/file_rules.csv can ignore a path pattern (for example a recycle bin) or give it a role.

3. Image time and time zones

  • DJI writes UTC in the XMP; that wins. Other cameras write local time in DateTimeOriginal with no zone.
  • For those, the shared time-zone table config/timezones.csv (ovid Core) gives the offset: one row per rule with serial, model, file_pattern, start, end, offset_hours and reason. Blank columns match anything; the first matching row wins.
  • time_utc = local time − offset. The rule used is kept in tz_rule.
Worked example. A senseFly S.O.D.A. image says 2024-07-12 09:15:00 with no zone. A row with model S.O.D.A., offset -7 and reason “camera on local summer time” matches, so time_utc = 09:15 − (−7 h) = 16:15 UTC.
  • A camera with an unusable clock (the Canon S110 often reads 1980) takes its time from a linked flown track (KML), and the flight’s time_source says so.

4. Flights

A flight is a run of images from one camera in one folder, split where exposures pause for more than 10 minutes (flight_gap_min).

new flight where t(i) − t(i−1) > flight_gap_min
Worked example. Exposures at 10:30:02, 10:30:04 … 10:41:58, then 10:56:10. The gap 10:41:58 → 10:56:10 is 14 min 12 s, more than 10 min, so the images from 10:56:10 on are a second flight.
  • senseFly images are grouped by the flight number in their names (<serial>_<flight>_<image>.JPG) or folder. Images with no number take it from the one flight number among the logs in their folder or the two above.
  • Sequoia writes four band images per capture; a flight counts both images and captures and is grouped by the camera’s FlightUUID.
  • The flight id comes from the camera serial and the first exposure in UTC, or from the flight number when the clock is unusable, so the same flight in another folder or source is the same flight.

Flight quality from the image headers (added October 2026)

Each image gets, where its headers allow, and each flight gets the median (on the Flight page and in flights.csv):

Value How it is worked out
Ground sample distance (gsd_cm) sensor width × height above take-off ÷ (focal length × image width), in cm per pixel. The sensor width comes from the EXIF focal plane resolution, or from a table of the archive's cameras (1-inch sensors 13.2 mm, 1/2.3-inch 6.17 mm, 1/1.7-inch 7.44 mm, full frame 35.9 mm). The height is DJI's RelativeAltitude, above the take-off point and not the ground under the image, so over slopes or water it is approximate; eBee images have no such height and no GSD.
Speed (speed_ms) DJI's FlightXSpeed and FlightYSpeed where written, otherwise the distance to the previous image over the time between them (images up to 30 s apart in one folder).
Motion blur (blur_px) speed × exposure time ÷ GSD, in pixels. Under about 0.5 to 1 pixel is the usual aim for mapping; blur_over_1px_pct is the share of a flight's images above 1 pixel.
Forward overlap (fwd_overlap_pct) 1 − distance to the previous image on the same line ÷ footprint along the track, taking the short side of the image as along the track (the usual layout for mapping flights). In a big folder only a sample of headers is read (30 images), so neighbouring images rarely both have a position; the flight's value is then estimated from its median speed × the median time between exposures, and fwd_overlap_source says "speed x interval" instead of "image pairs".
Side overlap (side_overlap_pct_median) 1 − spacing between neighbouring parallel lines ÷ footprint across the track. A line starts where the heading turns by more than 45° or images are more than 30 s apart. It needs the lines, so it is empty for big folders read from a sample of headers.
Sun elevation (sun_elev_deg) from the image's position and UTC time, to about a degree.

Nothing here is written into the images or used to change a status; it describes the flight for anyone re-using it. On the Samsung USB drive (scanned 6 October 2026) the three Zenmuse L2 flights of 22 September 2024 came out at a GSD of 1.6 cm (60 m above take-off), forward overlap 77 to 84 % (speed x interval), motion blur 0.6 to 0.8 pixels and sun elevation 23 to 27°. The eBee Plus flights with the Canon S110 have no height above take-off and no position in their EXIF, so none of these values can be worked out for them.

5. Missions

Sorties flown as one survey are grouped into a mission: the same aircraft flying again within an hour from the same plan or folder, or over the same area and site soon after (battery swaps, two flights on one battery). On the Flight page, Confirm this grouping or Split this sortie off; a mission name typed there groups sorties by hand.

6. Linking files to flights

Records are linked by what they say first: senseFly logs, eMotion geotags, plans and Pix4D projects by aircraft serial and flight number, or by the image names a geoinfo file or eMotion KML lists (score 0.95). Other files in the folder are scored:

Evidence Score
same folder as the flight +0.5
time in the file name within the flight +0.4
named after the folder +0.4
only flight in the folder +0.3
time in the file name outside the flight −0.3
state = auto if score ≥ 0.8 probable if 0.5 ≤ score < 0.8 suggested if score < 0.5
Worked example. A flight log in the flight’s folder (0.5) whose name holds a time 3 min after take-off (+0.4): 0.9, auto. A PDF report in the same folder with no time in its name, while two flights share the folder: 0.5, probable.

RINEX observations anywhere in the archive that span a flight are a probable link and never proof of correction. On the Flight page, each link can be confirmed or rejected with a reason (config/links.csv).

7. Positioning status

One of: RTK corrected, partly RTK corrected, PPK corrected, standalone GNSS / uncorrected, correction data available, not confirmed, unknown. A status typed on the Flight page (with a reason) wins; the found one stays beside it in positioning_found.

DJI (from each image’s RTK flag: 50 fixed, 34 float, 16 single):

fixed share = images with RtkFlag 50 / images with a flag ≥ 95 % → RTK corrected > 0 % → partly RTK corrected 0 % and onboard GNSS kept → correction data available, not confirmed 0 % → standalone GNSS / uncorrected no flag, Phantom 3 or 4 → standalone GNSS / uncorrected (no RTK on board)

senseFly (from geotag accuracy, CORRECTED_M = 0.1 m):

camera’s own geotag accuracy ≤ 0.1 m → RTK corrected metres in the camera, ≤ 0.1 m in eMotion’s geotags → PPK corrected metres everywhere → standalone GNSS / uncorrected (base or RINEX files alone never count as corrected)
Worked example. An eBee Plus flight: the S.O.D.A. images say 3.2 m horizontal accuracy; the eMotion geoinfo for the same images gives a median of 0.03 m. 3.2 m > 0.1 m but 0.03 m ≤ 0.1 m, so the flight is PPK corrected.

8. Geometry for the map

Kind Line style From
planned dashed KML/KMZ/WPML lines or areas without times
observed solid image positions, flown KML tracks, receiver positions
derived dotted extents worked out by ovid

Colour is the positioning status: RTK green, partly RTK cyan, PPK blue, uncorrected red, “available, not confirmed” orange, unknown grey (accent.vim).

Every map (Map page, GNSS page and the shared viewer) has a small Legend / PNG bar. Legend shows or hides the legend (remembered per map); PNG saves the view as it is on screen, with or without the legend, redrawn at 250 ppi: imagery tiles are fetched at the matching finer zoom and every shape is redrawn, so lines stay sharp.

9. Datasets: satellite, aerial and LiDAR

The Imagery page lists satellite scenes (WorldView, QuickBird, GeoEye, IKONOS .IMD; SPOT DIMAP), aerial photos, airborne LiDAR tiles (LAS/LAZ headers) and other georeferenced rasters, with platform, product, date (marked inferred when it comes from a name), ground sample distance, cloud cover and footprint. Footprints are drawn solid from vendor scene corners and dashed from file headers (UTM converted for display only). Only headers and sidecars are read. Catalogue: output/catalogue/datasets.csv.

10. GIS layers

Shapefiles, GeoJSON and GPX are listed on the Imagery page and drawn on the Map by kind from their names: GCPs and checkpoints, plots/transects/grids, boundaries and extents, field sites and trails, other. A shapefile without a .prj borrows its folder neighbour’s (marked inferred). Folders with more than 20 layers keep only extents.

11. GNSS survey points

On the GNSS page, upload survey files from Emlid Reach (point CSVs, .LLH, NMEA, Emlid Studio .pos, or the Emlid Flow zip), DJI RTK (point CSVs, Timestamp.MRK) or Leica (Viva / Captivate / LGO ASCII, GSI-8/16, LandXML). They are stitched into one table: exact repeats dropped, a point name reused with other coordinates flagged in note. Points with latitude and longitude are shown on the map; grid-only points need a UTM zone typed on the page. Export stitched points (CSV) writes ovid_rs_gnss_stitched_<date>.csv (also kept in output/gnss/). Coordinates are copied as found; nothing is converted.

Position quality (added October 2026)

Where a file gives them, each point also carries the number of satellites (n_sat; Emlid Flow's per-constellation counts are added up), pdop, hdop and vdop, the averaging samples, the age of the corrections in seconds (age_s), the baseline_m to the base and the correction type (NTRIP, LoRa and so on). Reach .LLH logs give satellites and age (the RTKLIB solution columns), and NMEA GGA sentences give satellites, HDOP and age. The GNSS page shows a table per file: points, share fixed, median horizontal and vertical RMS, median PDOP and HDOP, fewest satellites, oldest corrections and longest baseline. Values are copied as found; nothing is reprocessed.

12. QA

The QA page shows positioning status by year, missing metadata (site, project, sensor), flights with QA flags (no georeferenced images, positions only in eMotion geotags, camera clock unusable, MRK or RPT counts that differ from the images found, mission grouping uncertain) and files tied to no flight (unassigned.csv, with why).

Set-up check, time zones and file audit

These are shared with the other ovid apps and come from the core. Each run writes them to output/audit/, and the Sources page shows them in the Set-up check and file audit card.

  • Set-up check (setup_check.csv): sources (a source that is not plugged in is info, not an error), duplicate source ids, file rules that are not valid patterns, sites without a project, positioning statuses that are not on the list, links to files that no longer exist, and the time-zone table.
  • Time zones (config/timezones.csv): see section 3.
  • File audit (file_audit.csv): one row per file found with what_happened, either “in the catalogue: …” (as an image of a flight, a linked record, a dataset or a layer) or “not in the catalogue: …” with the reason (ignored by a rule, out of scope, not linked). Export it with Export file audit (CSV).

Exports from the app are named ovid_rs_<what>_<YYYY-MM-DD>.<ext>.

The viewer

One folder (and its zip) with index.html, a map, filters, summary cards and the flight table, plus flights.csv, links.csv and sources.csv. The person receiving it unzips it and double-clicks index.html; no R and no archive are needed, only the internet for map tiles. Image positions are thinned to 150 per flight (points_per_flight); flights marked exclude_from_archive are left out.

When something goes wrong

  • If part of a page fails, a notice says so with a short reference (E- and six characters) and the app carries on. The life-ring button collects versions, logs and the set-up into a troubleshooting zip (no raw data) to send with the reference.
  • If the output folder is deleted or moved while the app is open, the pages notice within seconds and show what is left; run again to rebuild it.
  • A project folder that cannot be written to (read-only, a locked or full drive), or a file where the output, cache or config folder should be, stops the run before anything is changed, with what to do.
  • A set-up table that is damaged or was saved by another program with columns missing is shown with those columns added empty and a notice; nothing changes in the file until it is saved.

Glossary

  • Flight: a run of images from one camera, split at pauses over 10 minutes.
  • Mission: flights flown as one survey.
  • Source: a drive or folder in the archive.
  • RTK / PPK: real-time or post-processed kinematic GNSS correction (centimetre positions).
  • RTK flag: DJI’s per-image fix state (50 fixed, 34 float, 16 single).
  • Geotag: the position written for an image, by the camera or later by software.
  • GSD: ground sample distance, the ground size of one pixel.
  • Footprint: the outline of a scene or flight on the ground.
